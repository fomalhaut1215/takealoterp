# ADR 0001: 采用微服务架构

## 状态
已接受 (Accepted)

## 日期
2026-09-30

## 背景

Takealot ERP 系统需要支持：
1. 多种业务模块（商品管理、订单履约、AI 服务、数据分析、客服系统）
2. 不同的扩展需求（AI 服务计算密集，订单服务 IO 密集）
3. 独立部署和迭代（功能模块可独立上线）
4. 第三方集成（Takealot API、物流商、AI 服务商）
5. 未来多平台扩展（亚马逊南非站、其他本地平台）

单体架构虽然开发速度快，但在扩展性、团队协作、技术选型灵活性上存在瓶颈。

## 决策

采用 **微服务架构**，按业务领域拆分为以下核心服务：

### 核心服务
1. **API Gateway** (网关服务)
   - 统一入口，路由请求到各微服务
   - 认证鉴权
   - 限流和熔断

2. **Product Service** (商品服务)
   - Offer CRUD 和批量操作
   - 与 Takealot API 集成
   - 库存同步

3. **Order Service** (订单服务)
   - 订单同步与状态追踪
   - 订单路由和拆分逻辑
   - 履约状态管理

4. **AI Service** (AI 服务)
   - 产品描述生成
   - 智能调价建议
   - 需求预测
   - LLM API 统一封装

5. **Analytics Service** (数据分析服务)
   - 销售报表
   - 真实利润计算
   - 库存健康度分析
   - 时序数据处理

6. **Customer Service** (客服服务)
   - AI 客服机器人
   - 退货工单管理
   - 多渠道消息聚合

7. **User Service** (用户服务)
   - 卖家账号管理
   - 权限和角色
   - 托管服务配置

### 技术选型
- **API Gateway**: Kong / Traefik
- **服务间通信**: gRPC (同步) + RabbitMQ/Kafka (异步事件)
- **服务注册与发现**: Consul / etcd
- **数据存储**: 每个服务独立数据库（PostgreSQL 为主）
- **容器化**: Docker + Kubernetes

## 后果

### 优势
✅ **独立扩展**: AI Service 可独立横向扩展，不影响其他服务
✅ **技术多样性**: 需求预测可用 Python，其他服务用 Go/Node.js
✅ **故障隔离**: 单个服务崩溃不影响整个系统
✅ **团队协作**: 不同团队可并行开发不同服务
✅ **未来扩展**: 添加新平台只需新增对接服务

### 劣势
❌ **复杂度提升**: 分布式系统调试困难，需要链路追踪
❌ **数据一致性**: 跨服务事务需要 Saga 模式或事件溯源
❌ **运维成本**: 需要 DevOps 能力和监控体系
❌ **初期开发慢**: 前期需要搭建基础设施

### 缓解措施
1. **初期简化**: MVP 阶段服务数量控制在 4-5 个
2. **数据一致性**: 优先使用最终一致性，避免分布式事务
3. **监控先行**: 从第一天起接入 Prometheus + Grafana + Jaeger
4. **本地开发**: Docker Compose 简化本地环境搭建

## 替代方案

### 方案 A: 单体架构
- **优势**: 开发速度快，部署简单
- **劣势**: 难以扩展，AI 服务和订单服务耦合
- **为何拒绝**: 不支持未来多平台扩展和独立扩展需求

### 方案 B: 模块化单体
- **优势**: 保持单体简单性，代码逻辑分离
- **劣势**: 仍然无法独立部署和扩展
- **为何拒绝**: 无法解决 AI 服务计算密集型扩展问题
